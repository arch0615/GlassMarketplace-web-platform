  2) FRONTEND IMAGE COMPRESSION
================================================================================

  WHY:
  Recetas (and now arreglo photos) come from phone cameras → often 5-10 MB.
  We already saw one Claude AI call fail because the image was 5.25 MB (over
  the 5 MB API cap). Compress on the client so we (a) save bandwidth on
  spotty mobile connections and (b) stay under provider limits.

  IMPLEMENTATION:
  ────────────────────────────────────────────────
  [ ] cd frontend && npm install browser-image-compression
  [ ] frontend/src/lib/imageCompression.js  (NEW)

      Provide a single helper:

      export async function compressImage(file, opts = {}) {
        if (!file?.type?.startsWith('image/')) return file   // PDF passthrough
        const { default: imageCompression } = await import('browser-image-compression')
        return imageCompression(file, {
          maxSizeMB: opts.maxSizeMB ?? 1,
          maxWidthOrHeight: opts.maxWidthOrHeight ?? 1920,
          initialQuality: 0.82,
          useWebWorker: true,
        })
      }

  [ ] Wire into all upload paths:
        - frontend/src/pages/cliente/NuevaReceta.jsx     (handleFile)
        - frontend/src/pages/cliente/NuevaArreglo.jsx    (new, from #1)
        - Anywhere else that uses <input type="file"> for images
          (catalog upload, dispute photos, etc. — grep for FormData
          to find them)
  [ ] Show a small "Comprimiendo..." spinner while running — typical
      compression takes 300-800 ms for a 5 MB image.

  RISK:
    - Compression is lossy. Receta legibility matters. Test with a
      real receta photo at 0.82 quality before shipping.

  3) LAZY REGISTRATION + UUID TOKEN FLOW   ★ BIGGEST ITEM ★
================================================================================

  WHY:
  Friction-free onboarding. Anyone can submit a request without creating
  an account; registration only happens at the moment of payment.

  CONCEPTUAL FLOW:
  ────────────────────────────────────────────────
  1. Visitor opens lensia.pro/ → clicks "Pedir presupuesto" (no login).
  2. Fills receta/arreglo form → end of form: Name, Phone, Email.
  3. Submit → backend creates QuoteRequest with status='open', client_id
     = NULL, guest fields filled, and a claimToken (UUID v4).
  4. Backend emails/WAs the visitor with link:
        https://lensia.pro/presupuesto/<claimToken>
  5. Visitor opens link → sees received quotes (PUBLIC, no auth).
  6. Visitor clicks "Aceptar presupuesto y pagar" → modal: "Creá tu
     cuenta para finalizar el pago".
  7. They enter a password (email/name/phone already known from step 2).
     Backend creates a User row, sets quoteRequest.client_id, clears
     guest fields, returns JWT.
  8. Now logged in → normal payment flow runs.

  DB CHANGES:
  ────────────────────────────────────────────────
  [ ] quote_requests
        - client_id  → nullable
        - guest_name: string | null
        - guest_email: string | null
        - guest_phone: string | null
        - claim_token: uuid, unique, indexed
  [ ] prescriptions
        - client_id → nullable (the upload happens before auth exists)
  [ ] (Optional) guest_contacts  table
        - If we want to dedup repeat guests by phone/email, store contact
          rows separately and link quote_request → guest_contact. Skip
          for v1; inline guest_* columns are fine for MVP.

  BE CHANGES:
  ────────────────────────────────────────────────
  [ ] auth/auth.controller.ts
        - New endpoint: POST /auth/register-from-request
          Body: { claimToken, password }
          - Reads QuoteRequest by token, validates not yet claimed
          - Creates User with guest data, hashes password
          - Updates QuoteRequest.client_id, clears guest_* fields
          - Issues JWT
          - Returns { token, user }

  [ ] requests/requests.controller.ts
        - Existing POST /requests stays for logged-in users.
        - New endpoint: POST /requests/anonymous  (NO @UseGuards)
          Body: CreateRequestDto + { guestName, guestEmail, guestPhone }
          - Validates guest fields (email format, phone format,
            non-empty name)
          - Validates the same CUIT uniqueness rules DO NOT apply
            (clients don't have CUIT at this stage)
          - Creates QuoteRequest with claimToken
          - Returns { id, claimToken }
        - New endpoint: GET /requests/by-token/:claimToken  (NO auth)
          - Returns the request + all its quotes (read-only)
          - Validates claimToken is a valid UUID v4 to avoid scanning

  [ ] quotes/quotes.controller.ts
        - GET /quotes/by-request-token/:claimToken  (NO auth)
          Returns quotes for that request.
        - Throttle this endpoint with @nestjs/throttler (e.g. 30 req/min

  [ ] prescriptions/prescriptions.controller.ts

  [ ] requests.service.ts → create() and notifyOpticas

            (and optionally guest_phone via WhatsApp, see #5).

  [ ] notifications.service.ts → new method:

    - claimToken is a v4 UUID (122 bits of entropy). Safe enough.
      DO NOT expose it in any analytics/logging system. Treat like a
      password reset token.

      a response that could be cached by a CDN. Use private cache
      headers and reject any query strings.
    - Rate-limit unauthenticated endpoints.
    - On register-from-request, if email already exists in users:
      reject with "Ya existe una cuenta — iniciá sesión" and offer
      login. After login, claimToken can be claimed by that user.

            duplicate claim attempt → conflict
    - E2E: full flow from landing to MP payment without ever logging in
            until the final click.

  4) ADMIN SUPPORT CHAT FROM EVERY ROLE
================================================================================

  WHY:
  Centralised support inbox so any user (cliente / óptica / médico) can
  message the admin directly without WhatsApp or external tools.

  DESIGN DECISION — TRANSPORT:
  ────────────────────────────────────────────────
  Three options:
    A. Polling every 10s on open chat. Dead simple. Good enough for MVP.
    B. WebSocket via @nestjs/websockets + socket.io. Real-time.
    C. Server-Sent Events. Lighter than WS, one-way only.

  Recommend (A) for v1 — under 5 hours of work. Upgrade to (B) only
  when admin volume exceeds ~50 active threads/day.

  DB SCHEMA:
  ────────────────────────────────────────────────
  [ ] support_threads
        - id           uuid pk
        - userId       uuid  (the non-admin party; cliente/optica/medico)
        - status       enum: open | closed
        - lastMessageAt timestamp
        - unreadForUser int  (count of admin → user messages user hasn't
                              read yet)
        - unreadForAdmin int
        - createdAt
  [ ] support_messages
        - id            uuid pk
        - threadId      fk
        - senderId      uuid (user id; admins all share the inbox)
        - senderRole    enum: user | admin
        - body          text
        - attachmentUrl string | null
        - readAt        timestamp | null
        - createdAt

  BE CHANGES:
  ────────────────────────────────────────────────
  [ ] modules/support/  (NEW MODULE)
        support.module.ts
        support.controller.ts
        support.service.ts
        support-thread.entity.ts
        support-message.entity.ts
        dto/send-message.dto.ts

  Endpoints (all JWT-protected):
        GET    /support/me                  → my thread (auto-creates if none)

  5) WHATSAPP NOTIFICATION CHANNEL
================================================================================

  WHY:
  Argentine users live in WhatsApp. Email gets buried; WA gets read.

  RECOMMENDED PROVIDER:
  ────────────────────────────────────────────────
  Twilio WhatsApp Business API
    Pros: best-in-class docs, single SDK with email-style API, $0.005-
          $0.0085 per message for AR.
    Cons: 24-hour template restriction (Meta rule). You can only send
          freeform messages within 24h of the user's last message;
          outside that window, you need a pre-approved TEMPLATE.

  Alternatives: 360dialog, Wati, MessageBird. Twilio is simplest.

  STEPS BEFORE CODING (cannot skip):
    1. Twilio account → enable WhatsApp sandbox first.
    2. Submit pre-approved templates to Meta via Twilio dashboard:
       - "Nueva solicitud asignada" (for ópticas)
       - "Nuevo presupuesto recibido" (for clientes)
       - "Cambio de estado de pedido"
       Templates can take 1-3 business days for Meta approval.
    3. Get production WhatsApp Business number approved by Meta
       (verify a phone number you don't already use elsewhere).
    4. Twilio gives you ACCOUNT_SID, AUTH_TOKEN, FROM_NUMBER.

  BE CHANGES:
  ────────────────────────────────────────────────
  [ ] cd backend && npm install twilio
  [ ] Add to .env:
        TWILIO_ACCOUNT_SID=AC...

                                   variables: Record<string,string>)
        - Methods notifyOpticaNewRequest / notifyClientNewQuote /

  [ ] users/user.entity.ts

  RATE LIMITING
  ────────────────────────────────────────────────

  ────────────────────────────────────────────────
  We're still running synchronize:true. For the lazy-flow changes,

  RECOMMEND before #3:
    - Turn synchronize OFF.
    - Generate one migration: `npm run typeorm migration:generate
      src/migrations/LazyRegistration -d data-source.ts`
    - Commit migration files to git.
    - Add `npm run migration:run` to deploy script.
  Time cost: 1-2 h once. Pays itself back the next time we change schema.

  TESTING STRATEGY
  ────────────────────────────────────────────────
  Per feature, add at least:
    - One unit test for the new service method.
    - One e2e test that hits the new endpoint(s).
  Lazy flow gets the most coverage:
    - Anonymous create → email/WA dispatched → claim token works once

  RISK REGISTER
================================================================================

  R1. Meta WhatsApp template approval delay
      Severity: MED   Likelihood: MED
      Mitigation: start approval flow on Day 1; ship Email-only until
      templates land.

  R2. Lazy-flow security: tokens accidentally indexed by Google
      Severity: HIGH   Likelihood: LOW
      Mitigation: emit X-Robots-Tag: noindex on /presupuesto/* responses;
      ensure no robots.txt opens it.

  R3. browser-image-compression quality too low for receta legibility
      Severity: MED   Likelihood: MED
      Mitigation: test with 5+ real receta photos before shipping; have
      a fallback path that skips compression if width < 1200 px.

  R4. Support chat polling load when many threads are open
      Severity: LOW    Likelihood: LOW
      Mitigation: poll only the user's own thread; admin inbox polls a
      summary endpoint every 15 s, not full threads.

  R5. Migration off synchronize:true breaks existing dev workflow
      Severity: MED    Likelihood: HIGH
      Mitigation: do the switch on a quiet day, keep a documented
      rollback (set synchronize:true + restart). Test migration twice
      in staging before prod.
